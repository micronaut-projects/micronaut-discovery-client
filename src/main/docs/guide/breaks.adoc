This section documents breaking changes between Micronaut Discovery Client versions:

=== Micronaut Discovery Client 5.3.0

==== Disabling Consul in tests

`micronaut.config-client.enabled: false` only disables the legacy bootstrap configuration client. If Consul is configured, other beans still contact it: the service is registered on startup, the `consul` health indicator reads the Consul leader, and the discovery client health indicator and `@Client(id = "...")` lookups query the catalog. Applications that used `micronaut.config-client.enabled: false` to keep tests away from Consul should set `consul.client.enabled: false` instead, which disables the whole Consul integration. See <<serviceDiscoveryConsulDisablingConsul, Disabling Consul>> for the individual switches.

==== Vault KV version default

Vault configuration now uses the KV version 2 engine when `kv-version` (or `vault.client.kv-version`) is not set, as documented. Previously, no Vault client was created unless the KV version was set explicitly.

==== Vault and Spring Cloud Config health indicators

Applications with `micronaut-management` now get a `vault` health indicator when the Vault configuration client is enabled, and a `spring-cloud-config` health indicator when the Spring Cloud Config client is enabled. A sealed or unreachable Vault, or an unreachable config server, reports the application `DOWN`. Disable them with `vault.client.health-check: false` and `spring.cloud.config.health-check: false`.

==== Eureka and Micronaut Serialization

The Eureka client now works with Micronaut Serialization as well as Jackson Databind, and in GraalVM native images. The Eureka model classes are introspected, and the JSON the client sends and reads matches the Eureka REST API with both libraries:

* The client adds and removes the `instance`, `application` and `applications` members that wrap Eureka request and response bodies. It no longer relies on the Jackson Databind root value wrapping features, which Micronaut Serialization does not support.
* `@JsonRootName` was removed from api:discovery.eureka.client.v2.InstanceInfo[], api:discovery.eureka.client.v2.ApplicationInfo[], api:discovery.eureka.client.v2.LeaseInfo[] and api:discovery.eureka.client.v2.DataCenterInfo[], so a mapper with root value wrapping enabled no longer wraps them.
* api:discovery.eureka.client.v2.ApplicationInfo[] is written with an `instance` member, as Eureka sends it, instead of `instances`.
* api:discovery.eureka.client.v2.AmazonInfo[] is written with the `com.netflix.appinfo.AmazonInfo` type id that Eureka uses, instead of the Micronaut class name, which Eureka could not resolve.

==== Zones in registration metadata

The zone set with `micronaut.application.instance.zone` is now registered under the `zone` key of the Consul service metadata and of the Eureka instance metadata, see <<serviceDiscoveryZones, Zones>>. A api:discovery.eureka.EurekaServiceInstance[] not running on AWS no longer returns its zone from `getRegion()` and `getGroup()`: they return the `region` and `group` metadata instead.

=== Micronaut Discovery Client 5.2.0

Consul may report a node, member or service address as a host name or as an IP address. The Consul client models used to map these addresses to `java.net.InetAddress`, which left the JSON library to resolve host names. Jackson 3.2, managed by Micronaut Framework 5.2, reads an `InetAddress` from IP literals only and no longer performs DNS lookups during deserialization, so responses with host names failed to decode.

The addresses are now kept as the strings Consul sends, and are read and written unchanged by both Jackson Databind and Micronaut Serialization:

* api:discovery.consul.client.v1.ConsulCatalogEntry[]: the `address` component is now a `String`. The constructor taking an `InetAddress` is deprecated.
* api:discovery.consul.client.v1.NodeEntry[], api:discovery.consul.client.v1.MemberEntry[] and api:discovery.consul.client.v1.AbstractServiceEntry[]: use the new `getHostString()` accessors. The `getAddress()` methods that return an `InetAddress` are deprecated. They resolve the address on each call, which may need a DNS lookup, and throw `UncheckedIOException` when it fails.
* `AbstractServiceEntry.address(String)` no longer resolves the address, so it no longer throws for a host name that cannot be resolved.
* A Consul service instance without a service address now uses the node address as Consul reports it, instead of the IP address its host name resolved to.

=== Distributed configuration migration note

Distributed configuration via the legacy bootstrap `ConfigurationClient` path is now deprecated. Prefer `micronaut.config.import` with explicit provider URIs such as:

* `consul://localhost:8500/config/application`
* `vault://localhost:8200/application`
* `springcloud://configserver:9000/hello-world/default`

Applications can continue using the legacy bootstrap path during migration, but startup will log deprecation warnings that point to the importer-based alternative.
