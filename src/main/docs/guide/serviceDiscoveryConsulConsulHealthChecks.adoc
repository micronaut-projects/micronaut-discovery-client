= Consul Health Checks

By default when registering with Consul Micronaut will register a https://www.consul.io/docs/agent/checks.html[TTL check]. A TTL check basically means that if the application does not send a heartbeat back to Consul after a period of time the service is put in a failing state.

Micronaut applications feature a link:{micronautapi}health/HeartbeatConfiguration[HeartbeatConfiguration] which starts a thread using link:{micronautapi}health/HeartbeatTask[HeartbeatTask] that fires link:{micronautapi}health/HeartbeatEvent[HeartbeatEvent] instances.

The api:discovery.consul.registration.ConsulAutoRegistration[] class listens for these events and sends a callback to the https://www.consul.io/api/agent/check.html[/agent/check/pass/:check_id] endpoint provided by Consul, effectively keeping the service alive.

With this arrangement the responsibility is on the Micronaut application to send TTL callbacks to Consul on a regular basis.

If you prefer you can push the responsibility for health checks to Consul itself by registering an HTTP check:

.Consul HTTP Check Configuration
[configuration]
----
consul:
  client:
    registration:
       check:
         http: true
----

With this configuration option in place Consul will assume responsibility of invoking the Micronaut applications https://docs.micronaut.io/latest/guide/index.html#healthEndpoint[Health Endpoint].

To let Consul monitor more than the overall health of the application, for example a database or a gRPC endpoint, you can register additional HTTP, TCP, gRPC or TTL checks. See <<serviceDiscoveryConsulCustomizingConsulServiceRegistration, Customizing Consul Service Registration>>.

== Consul health indicator

When `micronaut-management` is on the classpath, the api:discovery.consul.health.ConsulHealthIndicator[] contributes a `consul` entry to the https://docs.micronaut.io/latest/guide/index.html#healthEndpoint[Health Endpoint]. It reports `UP` with the current Consul `leader` when the Consul agent answers and `DOWN` otherwise. Disable it with `consul.client.health-check: false`.

Set `consul.client.health-check-services` to also report the catalog `services` (service names and tags) and the checks of the service registered for this application, looked up by `micronaut.application.name`:

.Reporting Consul services and checks
[configuration]
----
consul:
  client:
    health-check-services: true
----

The `service` detail contains the aggregated check `status` (`passing`, `warning`, `critical`, or `not-registered` when no instance is registered) and, for each instance, its ID, address, port, node and checks. The service checks are informational only and never change the reported status: Consul HTTP checks may call this application's health endpoint, so feeding their result back into it could keep a service failing forever. If the catalog or service queries fail, the error is reported as a `services-error` or `service-error` detail.
