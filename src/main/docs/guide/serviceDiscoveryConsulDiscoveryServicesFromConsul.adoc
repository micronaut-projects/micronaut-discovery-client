== Filtering Discovered Instances

By default service instances are looked up with Consul's `/v1/health/service/{service}` endpoint without any tag or filter. The following `consul.client.discovery` settings narrow down and tune that query:

.Filtering Discovered Instances
[configuration]
----
consul:
  client:
    discovery:
      passing: true
      consistency-mode: stale
      query-tags:
        inventory:
          - primary
          - v2
      default-query-tags:
        - production
      filters:
        inventory: 'Service.Meta.version == "2"'
      default-filter: '"canary" not in Service.Tags'
      datacenters:
        inventory: dc2
----

[cols="1,3"]
|===
|Property |Description

|`passing`
|Only return instances whose health checks are all passing (default `false`).

|`query-tags`
|A map of service ID to the tags to query with. Only instances that carry every tag are returned. Each tag is sent as a repeated `tag` query parameter.

|`default-query-tags`
|The tags to query with for services that have no entry in `query-tags`.

|`tags`
|Deprecated: a map of service ID to a single tag. Use `query-tags` instead. It is still honored when a service has no entry in `query-tags`.

|`filters`
|A map of service ID to a https://developer.hashicorp.com/consul/api-docs/features/filtering[Consul filter expression] sent as the `filter` query parameter.

|`default-filter`
|The filter expression to use for services that have no entry in `filters`.

|`consistency-mode`
|The https://developer.hashicorp.com/consul/api-docs/features/consistency[consistency mode] of the query: `default`, `consistent` (sends the `consistent` flag) or `stale` (sends the `stale` flag, allowing any Consul server to answer).

|`datacenters`
|A map of service ID to the data center to query.

|`schemes`
|A map of service ID to the scheme (`http` or `https`) used to call the instances (default `http`).
|===

These settings correspond to the `server-list-query-tags`, `default-query-tag`, `query-passing` and `consistency-mode` settings of Spring Cloud Consul.

The same options are available programmatically through the `findHealthyServices(service, passing, tags, dc, filter, consistencyMode)` method of api:discovery.consul.client.v1.ConsulClient[].

== Watching Service Instances

By default every lookup of a service, for example each request made by a `@Client` bound to it, queries Consul. To serve lookups from a local cache that Consul keeps up to date instead, enable the service watch:

.Watching Service Instances
[configuration]
----
consul:
  client:
    discovery:
      watch:
        enabled: true
        wait: 55s
        delay: 50ms
        retry-delay: 1s
        max-retry-delay: 30s
        idle-timeout: 30m
----

[cols="1,3"]
|===
|Property |Description

|`enabled`
|Whether the instances of looked up services are watched and cached (default `false`).

|`wait`
|The maximum time a https://developer.hashicorp.com/consul/api-docs/features/blocking[blocking query] waits for a change, sent as the `wait` parameter (default `55s`, Consul caps it at `10m`). The HTTP read timeout of the watch is derived from it.

|`delay`
|The pause between two blocking queries of a service, which protects Consul when a service changes very often (default `50ms`).

|`retry-delay`
|The delay before retrying after a failed query. It doubles with each consecutive failure (default `1s`).

|`max-retry-delay`
|The maximum delay between retries (default `30s`).

|`idle-timeout`
|When set, a service that has not been looked up for this long stops being watched; its next lookup starts a new watch. Eviction happens when the current blocking query returns, so within `wait` of the timeout. Not set by default: services stay watched until the application context closes.
|===

A service is watched from its first lookup until the application context is closed, or until `idle-timeout` elapses without a lookup. The first lookup waits for the initial, non-blocking query of the watch for at most the read timeout of the Consul client (`consul.client.read-timeout`, `10s` by default) and otherwise falls back to a direct query; later lookups are answered from the cache without contacting Consul. The watch keeps a blocking query on `/v1/health/service/{service}` open, built from the same `passing`, `query-tags`, `filters`, `consistency-mode` and `datacenters` settings as a direct lookup, and follows the `X-Consul-Index` header of each response. While the watch of a service is failing, lookups of that service query Consul directly until the watch recovers. Closing the application context cancels every watch.

When the watch observes that the instances of a service changed (an instance was registered or deregistered, or its address, tags, metadata or check status changed) it updates the cache and then publishes a api:discovery.consul.discovery.ServiceInstancesChangedEvent[] carrying the service ID, the previous instances and the current instances. The event is published on the `blocking` executor:

[source,java]
----
import io.micronaut.discovery.consul.discovery.ServiceInstancesChangedEvent;
import io.micronaut.runtime.event.annotation.EventListener;
import jakarta.inject.Singleton;

@Singleton
public class InventoryInstancesListener {

    @EventListener
    void onChange(ServiceInstancesChangedEvent event) {
        if ("inventory".equals(event.getServiceId())) {
            System.out.println("Inventory now has " + event.getInstances().size() + " instances");
        }
    }
}
----

The load balancers of `@Client` beans look instances up on each request, so they pick up changes as soon as the cache is updated. The watch plays the role of the catalog watch of Spring Cloud Consul and of the `refresh-period` cache of the SmallRye Stork Consul provider. Unlike the latter it learns of changes through blocking queries rather than periodic refreshes.

NOTE: `consul.client.discovery.watch` watches service instances. Watching configuration stored in the Consul KV store is configured separately with `consul.client.watch`, see <<serviceDiscoveryConsulConsulWatch, Consul Watch>>.
