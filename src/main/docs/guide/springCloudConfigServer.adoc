[[distributedConfigurationSpringCloud]]
https://github.com/spring-cloud/spring-cloud-config[Spring Cloud Config Server] provides server-side and client-side support for externalized configuration in a distributed system. With the Config Server, you have a central place to manage external properties for applications across all environments.

Micronaut includes native Spring Cloud Config client support for consuming Spring Cloud Config Server configuration.

The legacy bootstrap `ConfigurationClient` approach is deprecated. Prefer `micronaut.config.import` for new applications and migrations.

== Setup

The quickest way to start a Spring Cloud Config Server is to use to use https://github.com/spring-cloud/spring-cloud-config#quick-start[Spring Boot's Quick Start].

== Loading configurations from config server

The preferred process to consume configurations in a Micronaut application from a Spring Cloud Config Server is to use an explicit import URI:

.Importing configuration from Spring Cloud Config Server
[configuration]
----
micronaut:
  config:
    import: "springcloud://configserver:9000/hello-world/default"
----

To target multiple profiles or a Git label:

.Importing configuration with multiple profiles and label
[configuration]
----
micronaut:
  config:
    import: "springcloud://configserver:9000/hello-world/first,second?label=main"
----

For secured servers, prefer credentials in the URI authority:

.Importing from a secured Spring Cloud Config Server
[configuration]
----
micronaut:
  config:
    import: "springcloud://user:password@configserver:9000/hello-world/default"
----

Query-parameter credentials are also supported during migration, but URI user-info is preferred:

.Importing from a secured Spring Cloud Config Server with query parameters
[configuration]
----
micronaut:
  config:
    import: "springcloud://configserver:9000/hello-world/default?username=user&password=secret"
----

Treat import URIs with embedded credentials as sensitive values and store them accordingly.

=== Tokens and custom request headers

Besides Basic authentication, the Spring Cloud Config client can send the following with every request to the Config Server:

* `token` - sent as the `X-Config-Token` header, which the Config Server forwards to backends such as https://docs.spring.io/spring-cloud-config/reference/server/environment-repository/vault-backend.html[HashiCorp Vault].
* `bearer-token` - sent as `Authorization: Bearer <token>`, for example for a Config Server protected by OAuth2.
* `header.<name>` (import URI) or `headers` (configuration) - arbitrary request headers, matching Spring Cloud Config's `spring.cloud.config.headers.*`.

.Importing with a config token, bearer token and a custom header
[configuration]
----
micronaut:
  config:
    import: "springcloud://configserver:9000/hello-world/default?token=s.vaulttoken&bearer-token=oauth-access-token&header.X-Tenant=acme"
----

Structured import declarations accept the same options, with `headers` as a map:

.Structured import with tokens and headers
[configuration]
----
micronaut:
  config:
    import:
      - provider: springcloud
        uri: "http://configserver:9000"
        application: hello-world
        profiles: default
        token: s.vaulttoken
        bearer-token: oauth-access-token
        headers:
          X-Tenant: acme
----

Only one source of the `Authorization` header may be configured: Basic credentials (`username`/`password` or URI user-info), `bearer-token`, or an `Authorization` entry in the headers. Combining them fails with a `ConfigurationException`. The `X-Config-Token` header and other custom headers can be combined with any of them.

NOTE: Query parameter values are used as written in the import URI and are not URL-decoded.

=== Spring Cloud Config import URI reference

[cols="1,1,3"]
|===
|ConnectionString part |Example |Meaning

|Scheme
|`springcloud://`
|Selects the Spring Cloud Config importer.

|User info
|`springcloud://user:password@configserver:9000/...`
|Optional Basic-auth credentials. `username` and `password` query parameters are also supported, but user-info is preferred.

|Host and port
|`configserver:9000`
|Spring Cloud Config Server host and port.

|Path
|`/hello-world/default`
|Required. The first path segment is the application name and the second is the profile list. Multiple profiles may be comma-separated.

|Query string
|`?label=main&fail-fast=false`
|Optional importer settings.
|===

[cols="1,1,3"]
|===
|Option |Example |Description

|`label`
|`?label=main`
|Optional Git label or branch requested from the Config Server.

|`fail-fast`
|`?fail-fast=false`
|Whether failures should abort startup immediately.

|`username`
|`?username=user`
|Optional Basic-auth username. Prefer URI user-info instead.

|`password`
|`?password=secret`
|Optional Basic-auth password. Prefer URI user-info instead.

|`token`
|`?token=s.vaulttoken`
|Optional token sent as the `X-Config-Token` header, for example for the Config Server's Vault backend.

|`bearer-token`
|`?bearer-token=abc`
|Optional token sent as `Authorization: Bearer <token>`. Cannot be combined with Basic-auth credentials.

|`header.<name>`
|`?header.X-Tenant=acme`
|Optional request header sent with every Config Server request. Repeat for multiple headers.

|`retry-attempts`
|`?retry-attempts=3`
|Number of config import retry attempts handled by Micronaut's retryable importer support.

|`retry-count`
|`?retry-count=3`
|Alias for `retry-attempts`.

|`retry-delay`
|`?retry-delay=1s`
|Delay between import retries.

|`retry-max-delay`
|`?retry-max-delay=30s`
|Maximum overall retry delay.

|`retry-multiplier`
|`?retry-multiplier=2.0`
|Multiplier applied between retry delays.

|`retry-jitter`
|`?retry-jitter=0.2`
|Retry jitter factor from `0.0` to `1.0`.

|`read-timeout`
|`?read-timeout=5s`
|Read timeout for remote calls.

|`connect-timeout`
|`?connect-timeout=5s`
|Connection timeout for remote calls.
|===

The legacy bootstrap/client configuration is still available during migration. A complete example can be seen below:

.Registering your application as a Spring Cloud Config client
[configuration]
----
micronaut:
  application:
    name: hello-world
  config-client:
    enabled: true
spring:
  cloud:
    config:
      enabled: true
      uri: "http://configserver:9000"
      name: filename1,filename2

----

Optional legacy retry settings are also supported:

- `retry-attempts` specifies the number of retries
- `retry-delay` specifies the delay between retries

The legacy configuration also supports `spring.cloud.config.token`, `spring.cloud.config.bearer-token` and `spring.cloud.config.headers.*`, with the same semantics as the import options described above:

.Legacy configuration with tokens and headers
[configuration]
----
spring:
  cloud:
    config:
      enabled: true
      uri: "http://configserver:9000"
      token: s.vaulttoken
      bearer-token: oauth-access-token
      headers:
        X-Tenant: acme
----

The legacy integration uses the configured `micronaut.application.name` to look up property sources from the server configured via `spring.cloud.config.uri`.

The `name` field is optional in the legacy configuration. With `micronaut.config.import`, the application name and profiles are explicit in the URI path. See the https://spring.io/projects/spring-cloud-config/[Spring Cloud Config documentation] for server setup details.

== Config server health indicator

When `micronaut-management` is on the classpath and the Spring Cloud Config client is enabled (`spring.cloud.config.enabled: true`), the api:discovery.spring.health.SpringCloudConfigHealthIndicator[] contributes a `spring-cloud-config` entry to the https://docs.micronaut.io/latest/guide/index.html#healthEndpoint[Health Endpoint]. Like Spring Cloud Config's client side health indicator, it fetches the environment of the application from the config server, using the configured `name` (or `micronaut.application.name`), the active environments, the `label` and the configured credentials, and reports the names of the located property sources as details. The status is `UP` when the config server answers and `DOWN` otherwise.

To avoid fetching the environment on every health request, the result is cached for 5 minutes by default. Configure the time-to-live with `spring.cloud.config.health-check-time-to-live` (a zero duration disables caching), or disable the indicator with `spring.cloud.config.health-check`:

.Configuring the Spring Cloud Config health indicator
[configuration]
----
spring:
  cloud:
    config:
      enabled: true
      uri: "http://configserver:9000"
      health-check: true
      health-check-time-to-live: 1m
----

The retry settings of the client (`spring.cloud.config.config.retry-count` and `spring.cloud.config.config.retry-delay`) also apply to the health check.
