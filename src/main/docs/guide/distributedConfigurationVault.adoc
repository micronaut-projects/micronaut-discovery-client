[[distributedConfigurationVault]]
HashiCorp Vault can be used as a distributed configuration source for Micronaut applications.

The legacy bootstrap `ConfigurationClient` approach is deprecated. Prefer `micronaut.config.import` with explicit Vault paths.

== Importing configuration from Vault

.Importing a Vault secret path
[configuration]
----
micronaut:
  config:
    import: "vault://testtoken@localhost:8200/application"
----

.Importing an environment-specific Vault secret path
[configuration]
----
micronaut:
  config:
    import: "vault://testtoken@localhost:8200/application/prod"
----

.Importing from Vault KV v2 with an explicit path prefix
[configuration]
----
micronaut:
  config:
    import: "vault://testtoken@localhost:8200/application?kv-version=V2&secret-engine-name=backendv2-prefixed&path-prefix=mock/v2/path/prefix"
----

Query-parameter tokens are also supported during migration, but URI user-info is preferred:

.Importing a Vault secret path with a query-parameter token
[configuration]
----
micronaut:
  config:
    import: "vault://localhost:8200/application?token=testtoken"
----

Treat import URIs with embedded credentials as sensitive values and store them accordingly.

=== Vault import URI reference

[cols="1,1,3"]
|===
|ConnectionString part |Example |Meaning

|Scheme
|`vault://`
|Selects the Vault importer.

|User info
|`vault://testtoken@localhost:8200/application`
|Optional Vault token. The importer binds the URI username as `vault.client.token`.

|Host and port
|`localhost:8200`
|Vault host and port.

|Path
|`/application/prod`
|Required explicit secret path. Leading `/` is optional in practice, but the path must identify the secret to load.

|Query string
|`?kv-version=V2&path-prefix=config`
|Optional importer settings.
|===

[cols="1,1,3"]
|===
|Option |Example |Description

|`token`

|`kv-version`

|`fail-fast`

[[vaultAuthentication]]
== Vault authentication

By default the token configured with `vault.client.token` (or the import URI user-info) is sent with every request. Set `vault.client.authentication` to log in with another auth method when the application starts instead. The client token returned by the login is used to read configuration. Tokens obtained this way are not renewed, so they only need to outlive the configuration reads at startup.

[cols="1,3"]
|===
|`vault.client.authentication` |Description

|`TOKEN`
|Default. Uses the static token from `vault.client.token`.

|`APPROLE`
|Logs in with the https://developer.hashicorp.com/vault/docs/auth/approle[AppRole] auth method using `POST /v1/auth/{path}/login`.

|`KUBERNETES`
|Logs in with the https://developer.hashicorp.com/vault/docs/auth/kubernetes[Kubernetes] auth method, sending the pod service account token as the login JWT.
|===

.AppRole authentication
[configuration]
----
vault:
  client:
    uri: https://vault.example.com:8200
    authentication: APPROLE
    app-role:
      role-id: ${VAULT_ROLE_ID}
      secret-id: ${VAULT_SECRET_ID}
      path: approle
----

.Kubernetes authentication
[configuration]
----
vault:
  client:
    uri: https://vault.example.com:8200
    authentication: KUBERNETES
    kubernetes:
      role: my-app
      path: kubernetes
      service-account-token-file: /var/run/secrets/kubernetes.io/serviceaccount/token
----

[cols="2,1,3"]
|===
|Property |Default |Description

|`vault.client.app-role.role-id`
|
|AppRole role ID. Required for `APPROLE`.

|`vault.client.app-role.secret-id`
|
|AppRole secret ID. Optional when the role does not require one.

|`vault.client.app-role.path`
|`approle`
|Path the AppRole auth method is mounted at.

|`vault.client.kubernetes.role`
|
|Vault role to log in with. Required for `KUBERNETES`.

|`vault.client.kubernetes.path`
|`kubernetes`
|Path the Kubernetes auth method is mounted at.

|`vault.client.kubernetes.service-account-token-file`
|`/var/run/secrets/kubernetes.io/serviceaccount/token`
|File containing the service account token.
|===

The same options are available on `vault://` import URIs:

.Importing configuration with AppRole authentication
[configuration]
----
micronaut:
  config:
    import: "vault://vault.example.com:8200/application?kv-version=V2&authentication=approle&role-id=${VAULT_ROLE_ID}&secret-id=${VAULT_SECRET_ID}"
----

=== Custom authentication

To obtain the token in another way, for example with an auth method that is not supported out of the box, register a bean that implements api:discovery.vault.config.auth.VaultTokenSupplier[]. A user-defined bean takes precedence over the built-in one. The api:discovery.vault.config.auth.VaultAuthHttpClient[] can be used to call any `auth/{path}/login` endpoint, and api:discovery.vault.config.auth.AbstractVaultLoginTokenSupplier[] provides a base class that logs in once and caches the client token.

[source,java]
----
@Singleton
@BootstrapContextCompatible // <1>
public class GcpVaultTokenSupplier implements VaultTokenSupplier {

    private final VaultAuthHttpClient authClient;

    public GcpVaultTokenSupplier(VaultAuthHttpClient authClient) {
        this.authClient = authClient;
    }

    @Override
    public Publisher<String> getToken() {
        return Mono.from(authClient.login("gcp", Map.of("role", "my-app", "jwt", signedJwt())))
            .map(response -> response.auth().clientToken());
    }
}
----
<1> Required when the legacy bootstrap configuration client is used.

During migration, the older bootstrap configuration is still available:

.Legacy bootstrap Vault configuration
[configuration]
----
micronaut:
  application:
    name: hello-world
  config-client:
    enabled: true

vault:
  client:
    uri: http://localhost:8200
    config:
      enabled: true
----

Prefer the importer-based configuration for new applications and migrations.

The legacy bootstrap integration uses the configured `micronaut.application.name` to look up property sources from Vault.

.Legacy Vault configuration resolution precedence
|===
|Secret Path|Description

|`/application`
|Configuration shared by all applications

|`/[APPLICATION_NAME]`
|Application-specific configuration

|`/application/[ENV_NAME]`
|Configuration shared by all applications for an active environment

|`/[APPLICATION_NAME]/[ENV_NAME]`
|Application-specific configuration for an active environment
|===

With `micronaut.config.import`, the secret path is explicit in the import URI, so those default lookup paths are no longer implied. See the https://developer.hashicorp.com/vault/api-docs/secret/kv[HashiCorp Vault KV documentation] for server setup and secret storage details.

== Storing secrets in Vault

Micronaut reads each configured path as a single secret of the Vault KV secrets engine, and every key/value pair of that secret becomes a configuration property. Store all the properties of a path together in one secret rather than creating a secret for each property.

For example, to provide `datasources.default.username` and `datasources.default.password` to an application that imports `vault://localhost:8200/application/prod`, write both keys to the `application/prod` secret of the `secret` engine:

.Writing a secret with the Vault CLI
[source,bash]
----
vault kv put secret/application/prod datasources.default.username=postgres datasources.default.password=root
----

Writing `secret/application/prod/datasources.default.username` instead creates a separate secret below `application/prod`, which Micronaut does not read.

Secrets are read from the KV version 2 engine named `secret` unless configured otherwise, using `GET /v1/{secret-engine-name}/data/[{path-prefix}/]{path}`. For a KV version 1 engine set `kv-version` to `V1` (or `vault.client.kv-version` for the legacy integration), which reads `GET /v1/{secret-engine-name}/[{path-prefix}/]{path}` instead. The same layout applies to the paths the legacy integration derives from the application name and the active environments.

== Vault server URI

A `vault://host:port/...` import always connects to Vault over plain HTTP.

The legacy integration takes the Vault address from `vault.client.uri`, which must be a full URL including the scheme, for example `http://localhost:8200`. A value without a scheme, such as `localhost:8200`, is treated as the ID of a service to look up with service discovery, and startup fails with an error such as `No bean of type [io.micronaut.http.client.loadbalance.DiscoveryClientLoadBalancerFactory] exists`.
